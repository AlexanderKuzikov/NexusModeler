# NexusModeler — инструкции агентам

## Что это

Проект под **пропсы**: сорок нумерованных слотов рельефной модели и семь наборов, каждый заполняет все
сорок. Контракт, реестр слотов и требования к модели — в [`docs/CONTRACT.md`](docs/CONTRACT.md), читать
до работы. Это единственный источник истины по слотам.

**Содержимое наборов — владельца.** Не выдумывать новые слоты, не переставлять номера, не добавлять
свои `kind`. Задача от штаба или от владельца описывает только форму.

## Форма проекта

Три файла в корне, без сборки и без рантайм-зависимостей, как в `NexusDefense`:

- `index.html` — разметка, стили, `importmap` на three.js с CDN, весь движок и витрина;
- `slots.js` — реестр слотов и параметры форм;
- `sets.js` — наборы: какая форма стоит в каком слоте.

**Ни одного ES-модуля на `file://`** не заводить: модуль с `file://` не грузится. Либо всё внутри
`index.html`, либо обычные `<script>`. `three` с CDN или вложенный — как договоримся при сборке.

Проверка изменений: `python serve.py 8802`, затем витрина глазами. Тест-раннера нет и не изобретается:
проект без зависимостей, проверка — открыть витрину и пройти сценарий.

## Команды

```bash
# сервер витрины
python serve.py 8802

# проверка данных без зависимостей: слоты, наборы, ссылки наборов на формы
node tools/check-slots.mjs
```

## Правила написания моделей

- **Параметризация, а не копипаст.** Слот — это место в наборе: одна форма, разные параметры на
  каждый сет. Сорок отдельных несвязанных моделей — это не работа, а сорок работ.
- Форма читается **силуэтом**. Проверка на витрине — с расстояния, а не вблизи.
- **Комментарии только там, где инвариант или грабли.** Комментарий «что здесь происходит» не пишется.
- Стиль кода как в `NexusDefense`: 2 пробела, `const`/`let`, стрелки, без `var`.
- Цвета — `setHex(0x…, THREE.SRGBColorSpace)`. Значение `0x…` без указания пространства читается как
  linear и будет темнее в 2.2 раза.
